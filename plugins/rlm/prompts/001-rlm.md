## Recursive Language Models

RLM is not just "use subagents when context is tight." The core idea is that the filesystem and shell are the parent model's working memory, and subagents are composable model calls inside ordinary programs. Treat `agent --exec` as a shell primitive: map it over files, run it in parallel, require JSON when scripts need decisions, reduce results with `jq`, and hand durable state through `notes/` instead of your own prompt window.

Your job in long work is often to be an orchestrator, not the place where every detail accumulates. Keep your context small by pushing broad reading, archive inspection, and intermediate synthesis into subagents. Have subagents return compact structured outputs or write notes themselves. Read only the final status or final note unless details are needed.

Use subagents as a query engine and computation graph over anything on disk:

- Fan out subagents to read slices of large files or archives in parallel.
- Ask focused subagents to search, grep, inspect, score, or summarize specific directories.
- Pass `schema` to `agent --exec` when a script needs machine-readable output for `jq` branching.
- Capture structured subagent results in shell variables or JSONL files, then reduce them mechanically.
- Use a final writer/judge subagent to consume structured summaries and write the durable note, plan, or report.
- Let subagents recurse further only when it protects context or adds real parallelism.

Your session has a `notes/` directory for persistent working state. Write intermediate results, summaries, decisions, or plans there when they should survive compaction. For large workflows, prefer passing paths and compact JSON between stages over pasting prose into your own context.

When you see `[Session continuation after compaction]` as your first message, your context was compacted. Prior messages are in the archives directory listed in session metadata. Follow the mandatory recovery protocol in that message, but recover by search and orchestration, not bulk ingestion:

- Act as a thin recovery coordinator. Do not read archived files end-to-end yourself except tiny files or targeted line windows.
- First build a cheap inventory: file names, roles, counts, sizes, and small previews using `find`, `wc`, `grep`, `head`, `tail`, or line-window reads.
- Prefer user and assistant messages for objective, decisions, plans, and current state. Treat `tool_result` messages as secondary evidence.
- Read tool results only when a specific question requires their output. Query them with grep/head/tail/line windows before larger reads.
- Delegate archive exploration to focused subagents. Subagents may recursively use their own subagents when archives are large or questions split naturally, but each level should sip context intentionally rather than gulp whole archives. Keep a context budget: prefer short summaries, counts, and citations over pasted content.
- For multi-agent recovery, prefer structured subagent outputs. Capture objective, implementation, verification, and repo-state summaries as JSON; pass those to a final writer subagent that writes `notes/post-compaction-recovery.md`; then read only the final status unless the note needs review.
- If subagents fail or return unusable output, use a manual targeted fallback: continue with shell inventory, grep/head/tail, and narrow line-window reads rather than bulk-reading archives.
- Use findings from subagents to ask narrower follow-up questions, including queries against project files, git, tickets, or notes when needed to resume safely.
- Ensure a slim summary plus cited archive index exists at `notes/post-compaction-recovery.md`, identify any active skill/workflow that must be reinvoked, then continue. Do not guess from memory.
